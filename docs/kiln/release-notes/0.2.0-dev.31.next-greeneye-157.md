# Kiln 0.2.0-dev.31.next: Greeneye mods read the game's own code beside other hooks (GitHub #157)

Greeneye Loader mods such as Hollow Halls Progression now read the same game code they found, also where another mod
or Kiln has hooked the game.

## Players and server admins

- **Hollow Halls Progression should start beside ShroudForge mods again.** On 31.24 it stopped at the start with
  "unsupported game signatures; no map menu", and the launcher listed it as "did not start". That start had a
  ShroudForge mod switched on (fcu-render-observer), so Kiln hosted ShroudForge, and its runtime and Kiln's own newer
  hooks had changed some of the game's code. Kiln's Greeneye host still found the game code the mod asked for, but
  when the mod then read bytes inside that code, it got those hooks' jumps instead of the game's own bytes. Now it gets
  the game's own bytes, the same ones it found. The same Hollow Halls Progression started on the same game build under
  Kiln 0.2.0-dev.29.19, without those hooks. Thanks to Dark-Thoughts for the report (kiln#157).
- **When a Greeneye mod still does not start, kiln.log says more.** Just before "did not start" there is now a line
  with how many game signatures the mod asked for, which ones were not found, and where Kiln read the game's code.
  If every signature was found, the line says the mod declined for a reason of its own; its own lines above say which.
  Send a support report (Logs > Save report) with it.
- **Greeneye mods keep the game's own code when Kiln's Greeneye host cannot open the game's exe.** It now uses the copy
  of the game's code that Kiln itself checked at start, instead of the code as other mods left it. This was one of the
  suspects in this report (the game's folder can be reached by several paths on Linux). The report points elsewhere:
  Kiln opened the same exe at the same path in that start. Still, the host no longer depends on that second read.

## Modders

- No mod API change: mod API 0.2.26.
- **GreeneyeHost `read` returns the code `find` matches** (`native/plugins/greeneye/src/find_code.h`). `find` matches the
  exe file's relocated `.text`, so another module's hook cannot hide a signature. `read` returned the live bytes with
  only Greeneye's own hooks laid back, as Greeneye Loader does. Under a Kiln detour, a hosted ShroudForge hook or
  another loader's jump, a mod that found a pattern and read an operand inside the match (a call's target, a global's
  displacement) got the hook's bytes. Now `read` returns the exe file's bytes under every recognised hook form: a jump
  to outside the image with the nops behind it, or a call sent outside the image. That includes hooks written after the
  first `find`. A byte another mod changed in place is still the live one, as in `find`. A place with too many in-place
  changes to sort (more than 1% of the 4 KiB on each side of the read), and every read while `find`'s code is the live
  snapshot, return the live bytes as before. The lab probe's `lab_read` check expects the file's first byte now. See
  docs/kiln/engines/greeneye.md, "Why `read` differs from Greeneye Loader's".
- **`find` without the plugin's own exe read.** When kiln-greeneye cannot open, map or match the exe file, it reads
  the same code through kiln.hooks `read_original` (Kiln's verified view, the code sigdb scans), 64 KiB at a time, and
  keeps the live code's in-place changes as before. Only without both does it fall back to the live snapshot and the
  lookup behind hook jumps.
- **kiln.log for a mod that does not start.** `[greeneye] <name>: while starting it asked find for N signatures in the
  game's code (<source>); not found: K ("<pattern>", ...); M reads returned the game's own bytes under another module's
  hook (rva 0x..., ...)`. Up to four patterns (72 characters each) and four places are named. `<source>` is `exe file`,
  `exe file (Kiln's view; the plugin's own read: <why>)` or `live: <why>`. A mod that starts gets the reads part only,
  and only when it has such reads. Quick Deposit's startup line uses the same `code=` words.
- `kiln::pe::other_differences` (`native/core/src/pe_text.h`) takes an optional code section span, so a redirected
  call is still a hook when only a window of the code is compared and its original callee lies outside that window.
  Without the span it behaves as before.

## Not yet seen in a real game

- Not tried with Hollow Halls Progression in a game. Its DLL is not in Kiln's tests. From the report: the same DLL
  (sha256 0e08ac7e...) started on the same game build (26430625) under Kiln without hosted ShroudForge. Over a copy of
  client 26430625 with the player's 135 hooked places rebuilt, `find` saw no byte different from the exe file. Reads of
  74 patterns over those places gave the hooks' bytes before this change and the game's own bytes after it, ShroudForge's
  two main menu call relays included. If it still does not start, the new kiln.log line names the signature or the read.
- The fallback to Kiln's view of the exe has not run in a game: the plugin's own read has worked in every report so far.
