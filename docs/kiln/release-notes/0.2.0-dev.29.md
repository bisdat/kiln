# Kiln 0.2.0-dev.29

OnBoot now runs in a player's game, not only on a dedicated server. In 0.2.0-dev.28 a mod with `"boot"` (for example More Flame Altars) loaded on a dedicated server but not in a game that hosts a world or joins a server, unless `"preview"` was set in `kiln.json`. That was a mistake in the release: the capability had been tested in a real game and should have shipped on.

## Players

- **Boot mods load in your game.** A mod that changes the game's data before the game reads it (More Flame Altars and others built on OnBoot) now works in a world you host and when you join a server, with no setting. If you added `"preview": ["mods.boot.client", "mods.boot.resource_patches"]` to `kiln/kiln.json` for dev.28, it is no longer needed; leaving it does no harm.
- **Server owners: when Kiln stops a server's start** (exit status 1 or 2 under Wine, 19201 or 19202 on Windows: a boot mod that is required failed, or the mods' NPC roster does not fit), do not restart it; fix the mod list. `kiln.log` and `kiln/state/` say which mods. The release's `kiln@.service` no longer restarts on these two statuses (`RestartPreventExitStatus=1 2`); tell a hosting panel the same. Under Wine statuses 1 and 2 also come from ordinary failures, so a server kept down this way may have failed for another reason: read `kiln.log` before starting it again.
- A dedicated server that runs a boot mod its players need no longer turns away players who have Kiln and the mod: their game now loads it.
- **Test builds from the launcher (the beta channel).** Settings > Updates > Channel has "Beta (test builds)". Choosing it switches the launcher to the newest test build of the next release in one step; "Switch back to the release", in the same place and behind the Beta mark in the header, goes back the same way. That switch back is the only time the launcher installs an older build, and only when you ask for it. At the first start of a test build the launcher keeps a copy of your profiles and settings from before the beta and offers it back when you return. After a switch back, the next Play first puts the release's Kiln into the game. Nothing changes for players who never choose Beta.
- **When ShroudForge runs from its own loader, Kiln says so.** If ShroudForge's own loader file is in the game folder, ShroudForge runs its mods itself and your profile's ShroudForge switches do not apply. The launcher now shows that where you look: the Engines view's ShroudForge row reads "runs itself" with the file's name, and the mod list shows one notice when your profile has ShroudForge mods, with the way out (remove that file, or let Kiln manage ShroudForge). `kiln.log` has one line for it at each such start. Nothing about what loads has changed.
- **When Kiln stops the game's start, the launcher says why.** Kiln ends a start before any world loads when going on would cost a world its mods' progress (the mods' NPCs do not fit the Survivors roster, or a boot mod the profile requires failed). Where the launcher used to go back to Play as if you had quit, it now shows "Kiln stopped the start" with the reason, the mods by name and a button to the mod list filtered to them; `kilnctl run`, `start` and `status` print the same reason.
- **Updating a mod keeps the version you had.** After an update, the mod's menu in the launcher offers "Roll back to <version>": the earlier version comes back with the settings it had when you updated. Kiln keeps one earlier version per mod and profile by default (Settings, "Earlier versions to keep", 0 to 5; `kilnctl library rollback` does the same from a terminal). A setting you change after a roll back stays yours: Kiln only puts back a settings file that is still as it was before the roll back. If the launcher or the PC stops in the middle of an update or a roll back, the next start finishes it or puts everything back. Not covered: a real power cut has not been tested (only the order in which things are written), and a mod whose folder you placed by hand is never taken over.
- **Replace a mod's DLL without rebuilding its zip.** A DLL mod's menu in the launcher has **Replace DLL…**: choose the patched DLL you got from the mod's author or its forum, and Kiln makes a new build of the same mod with that file swapped. The mod keeps its place in your list, its switch and its settings, and the build you had is kept: **Roll back to … (earlier build)** returns to it. Adding a bare DLL as before still makes a new mod. Not run on Windows yet.
- **A way out when another mod loader left its files in the game folder.** If Kiln's EML mods all fail because the game folder holds game data and backups another loader made, the launcher's Engines view (Logs, Engines) now offers **Restore the game's data**: verify the game files in Steam, then Kiln lists the leftover files and moves them into a folder under `kiln/eml/displaced`. Nothing is deleted, and **Undo move** puts them back. If Steam repaired files, start the game once more before the move: Kiln reads the list of leftover files at a start. It is not offered while ShroudForge prepares the game's data for your profile, and it has not run on Windows or on a real game folder yet: if it does not appear or refuses, the manual way still works (move the extra `enshrouded_NNN.dat` files and the two `.bak` files out of the game folder).
- **Filter boxes can be cleared.** The launcher's filter and search boxes (the mod list, Logs, a server's Mods, its console and Kiln commands, the Catalog and the item search) have a clear (X) button while they hold text, and Esc empties them. Esc in an empty box still closes the dialog it is in.
- **Linux, without Kiln's launcher:** starting the game from Bottles, Lutris or plain Wine needs `dinput8` set to native, builtin. With Ultimate ASI Loader next to Kiln, set `xinput9_1_0` as well (`WINEDLLOVERRIDES="dinput8,xinput9_1_0=n,b"`). [engines.md](../engines.md) says what was tested.
- **Linux (Wine, Proton):** when Wine loads its own copy of a DLL in place of one Kiln chains (Ultimate ASI Loader as `xinput9_1_0.dll` is the known case), `kiln/logs/proxy.log` (or `kiln.log` for a `[late]` DLL) now says so and names the override to set, for example `WINEDLLOVERRIDES="xinput9_1_0=n,b"`. Before, the log said "loaded" while the mod never ran.
- **Mods can swap a whole set of gear at once:** rings, armour, arrows and the rest change together or not at all.
- **Mods can add up to 93 recruitable NPCs** (29 before). A world whose mods add more than 29 needs Kiln 0.2.0-dev.29 or later on the server and in every player's game: an older Kiln refuses those mods' NPCs and quests, and that world loses their progress once it is saved. If your mods add more NPCs to the Survivors roster than Kiln can hold on your game, the game now closes at its start and names the mods, before any world loads, so your save keeps its progress.
- **Boot mods are compared when you join a server.** Kiln checks that each boot mod you both have made the same game data in your game as on the server, for example the Flame Altar limit More Flame Altars takes from its settings. If your settings differ, you join with a warning that names the mod (a server set to refuse turns you away with the same message): use the server's settings of that mod and restart the game. Not yet seen between a real server and a real game: if you get this warning with the same settings as the server, tell us.
- **Servers can carry many more mod buffs** (room for 4,096 added buffs, 1,024 before). As before, joining such a server needs Kiln and the same mods. If your game cannot hold as many added buffs as the server uses, the server now turns you away at the join and says how many it uses and how much room your game has, where before you could get in and see wrong or missing buffs.

## Mod authors

- **New: events a mod can refuse (`kiln.decisions`).** `EntityDyingEvent` (a death from health), `ItemPickingUpEvent` (a walk-over pickup) and `PlayerEquippingEvent` (an equipment input) can be canceled by a listener; the game's own handling runs when nobody cancels or a listener does not answer in time. The hooks go in at your first `Events.On` (the capability reads pending, then available; if they cannot be placed safely the row lowers and `CapabilityChangedEvent` tells you). Only the server world's deaths and pickups are held. A refused death keeps the entity alive after one step at 0 health; a walk-over allow is one attempt, and a failed one (no room) asks again. A fault shuts the service down for the process and open decisions end `CapabilityReleased`; a rollback of entity ids ends them `StaleEntity`. Guide: `docs/kiln/services/decisions.md`; sample `mods/samples/Decisions`.
- **New `Kiln.Systems`: wrap the game's own ECS programs.** `Systems.Wrap("fuel_setup")` runs your code before, after or instead of one of the game's programs, by name, per slice (`Before`, `After`, `Replace`) or per entity (`BeforeEach`, `AfterEach` with an `EntityView`: `Has`, `Read`, `Write`, `Attribute`), in the program's own place and on its own thread. Writes through a view reach the save and other players and raise `ComponentWrittenEvent` with `Writer = "<modid>/wrap:<program>"`; `Attribute32.Changed` runs the game's attribute formulas. Handlers run on the game's worker threads once a second player is in the world: tick-thread APIs throw inside them, use `slice.Post`. One `Replace` per program (a second is refused and names the holder); wraps are refused while native SET is loaded. A throw turns off that stage only (both halves of an `AroundEach`). Guide: `docs/kiln/modding/ecs-programs.md`, "Wrapping the game's programs".
- **Typed program wraps.** `Systems.Wrap<Ecs.Programs.FuelSetup>()` gives a per-entity stage a typed view of one of the game's programs and its components (802 views on this game build, in `Kiln.Game`, namespace `Kiln.Ecs.Programs`), checked against the running game: a program a game update changed is refused, and the reason names the lists that changed; a component whose layout changed is refused before it is read or written. `AroundEach(capture, apply)` runs your code on each entity just before and just after the game's own update. Sample: `mods/samples/WaterWorks` (wells refill faster); template: `kiln new system-wrap`.
- `WhenArchetype` now matches on a real server (in the first build of `Kiln.Systems` it matched nothing there), and a filter that cannot decide turns its stage off with a reason instead of skipping every slice. The filter reads each slice's archetype from the game's own record of that slice (a link around the game's program runner, put in a step after the first stage asks; the record is taken for one call and restored on every way out). On a server, until that link is in or where it cannot be resolved, it falls back to the entity map, checking it again after the read: when three reads in a row saw the map change under them, that one slice is left to the game (counted in `WrapStats.ArchetypeSkips`, said once per stage in `kiln.log`) and the stage stays on; the fallback narrows the window, it does not close it, and relies on the game applying entity creation and removal at the end of its step. In a game client the filter never reads the entity map: it leaves a slice to the game until that slice's own record can be read, and turns itself off with a reason where it cannot.
- **A world's stop waits for the world's jobs on a game client too.** When you leave a world, Kiln now calls the game's own wait for that world's jobs before mods hear the world stop, as it already did on a server, and the game never lets a program's slice run past the step that started it; so a wrap stage or a client-world program is not still running when its world is freed. The rows `world.stop_drain.server`, `.client` and `.prediction` say whether this build has that wait; where it is missing, wraps have a 2-second safety wait only, which does not keep the world alive. The wait itself has no time limit: if it ever stalls, `kiln.log` says "still waiting for world jobs" after 5 seconds and then more rarely. If Kiln's tick hook faults, program wraps stop at once and the game's own updates run as without Kiln.
- `Spawn` and `Destroy` called inside a program wrap's stage or a Kiln ECS program are refused, on the world's own thread too, with a message that names `slice.Post` (or `Scheduler.Post`): creating an entity in the middle of the world's step changes the entity map under the game's workers. Inside a `GameSystems.Hook` callback such calls still go through as in 0.2.0-dev.28, with a warning in `kiln.log` once per mod and call kind (once per call kind for a native caller); EMF's own `hook_program` refuses them as upstream EMF does.
- **Program wraps run under `dotnet test`.** `KilnHarness.Programs` declares the game programs your mod wraps, or a Kiln.Game view with its contract, and each harness step runs your stages over the fake world's entities (Before, Replace or the update, After, per-entity views, marks, `WhenArchetype`, `ComponentWrittenEvent`). The kit times each stage against the 1 ms budget and turns a stage off after ten overruns in a row, as the game side does; it does not model `Systems.Define`, client-world wraps, the worker threads or a native fault.
- **`Systems.Define`: a program of your own.** Write a `[Query]` struct; the build writes it into `kiln.programs.json` (a wrong entry stops the build with KILN036), kiln.world reserves it when the server starts, and `Systems.Define<T>(key, options, each)` binds your handler, which then runs once per matching entity on the game's workers. A key that was not reserved at boot answers `Ok = false` ("rebuild the mod and restart the server"), and so does a `[Query]` that differs from what was reserved at boot (another filter, another required or optional component, other flags): the answer names the first difference, because a rebuilt declaration is in the game only after a server restart. Your handler cannot call tick-only APIs while it runs, as in a wrap. `systems.define` says whether it is available.
- A per-entity stage whose program lists could not be read in time is suspended with the reason and tried again at the next steps (eight times) before it is turned off; it used to be off for good after one miss.
- The SDK's programs step: removing the last `[Query]` removes the generated `kiln.programs.json` from the output, an unchanged file is not rewritten, and two `[Query]` structs with one key stop the build (KILN036).
- `WhenArchetype` checks that the entity's record still names the entity it looked up before it trusts the record: the game frees a removed entity's record at once and may hand it to a new entity. A record that now names another entity is read again, three times in all, and then that one slice is left to the game; the stage goes off with a reason only when the filter cannot decide at all on this build (no archetype to read, or an unknown component name).
- In a game client, `new WrapOptions { World = WorldKind.Client }` wraps the client world's programs.
- `kiln.mod.json` takes `"systems": { "replaces": [...] }` (a declaration for tools; nothing reads it yet).
- Native mods: `kiln.world` gains `register_program_world`, `program_world_state`, `bind_program_world` and `unbind_program_world` at offsets 496 to 520, after the foreign views (the table is 528 bytes, version 4 stays).
- Native mods: `kiln.world` v4 gains per-entity members for a wrap stage (`game_program_list`, `game_slice_iterate`, `_slot`, `_mark`, `_archetype`, `game_archetype_has`, `game_slice_attr_changed`, `game_slice_attr_validate`, `game_world_session`, `game_program_contract`), appended after `in_program`. Before you free anything a stage uses, call `game_wraps_release` and poll it until nothing is pending.
- **Typed hooks and typed calls (`Kiln.Sigs`, `Hooks.Detour`, `Invoke`).** A typed hook is written into the game only after Kiln has checked every game thread: one asked for during a step is pending until the next safe tick (`HookResult.Pending`, `HookHandle.State`, `HookHandle.Reason`), and if the threads cannot be checked Kiln tries at three safe ticks, then the handle says `Refused` with the reason and `HookRefusedEvent` is posted. `Invoke` checks the descriptor it was compiled with against the game it runs in before it calls. An exception in a handler is caught and the game gets the original's result, also a result returned in a buffer. A null reference in a handler's own C# code is caught like any exception; any other access violation (in native code the handler calls, or at another address) still ends the game, as anywhere in managed code. While a world is running at most four typed hooks go in per tick (each first hook on a game function briefly stops the game's other threads for the check), so a mod that asks for many gets them over a few ticks; with no world running there is no limit. On a busy lab server a pass-through hook cost tens of nanoseconds a call and an `Invoke` about 0.3 µs.
- **Impact natives that answer in the same step.** `Abilities.Natives.RegisterSync` registers a native that answers inside the program's call (server only, `abilities.natives.sync`); the older natives still suspend the program for one step. `Abilities.Natives.Attach` hooks a vanilla native's calls in one program at one call site, Before, Instead or After, without cloning the program (`abilities.natives.attach`); `Natives.Wrap` and `OnDamage` now run through it, unchanged. A `natives.json` entry with `"sync": true` binds its argument types: Kiln and the cook refuse mismatched programs (E_ARGTYPE) and every call is checked; `Natives.DeclareTyped` does the same from C#. Kiln's two built-in natives and all mods' natives share 21 entries of the game's native registry (it takes 128, 107 of them the game's own), so 19 are left for mods: a registration past that is refused with the reason, where before it was silently left out.
- **Watch components for changes (`ComponentChanges.Watch`, Kiln.World).** A watch covers Health, Stamina, Mana, Fuel, Inventory and SlotSelection of up to 128 entities, or of every player, optionally with their linked inventories and items. Each step it posts one `ComponentValueChangedEvent` per changed component with the bytes before and after and an origin: `Kiln` with the writer's id (your mod, `kiln.combat`, `kiln.items`), `Mixed`, or `Unknown`; a change is never called the game's. `AttributeValueChangedEvent` carries typed values, `ComponentWatchStateChangedEvent` says when a watch is suspended and why. It is a net-change observer of the server world: a component larger than 256 bytes reads as absent, a watch that joins a pair another watch already covers splits that step into two records, and an item that left and came back unseen with the same id cannot be told from the one before. Budgets are shared by all mods, first come first served: 32 watches, 4,096 present pairs, 128 roots a pair; a watch that does not fit is refused with the reason and one that grows past them is suspended whole. Nothing runs for it unless a mod watches; writers pay only for watched entities (`events.component_net`; the test kit fakes it with `KilnHarness.ComponentChanges`).
- **Your own ECS program in the player's client world.** A client or both mod can run a program in the client world or in the prediction storage: declare it in `kiln.programs.json` with `"world": "client"`, `"both"` or `"prediction"` (a file without the field means the server world, as before) and bind it with `EcsPrograms.TryBind(key, callback, WorldKind.Client)` in `OnLoad`. It runs in that player's game only; other players and vanilla clients see nothing of it. In a client world or the prediction storage `TryWrite` does not mark the write for the save or for replication, and `TryWriteOther` answers false. The native side follows: in a client program `mark_written` does nothing, and `foreign_write` and `foreign_attr_changed` refuse. A bind in a process whose client programs were switched off throws `KilnUnavailableException` with the reason, and a client callback that threw is reported again in every later client world. `EcsProgramRefusedEvent` and `ClientComponentWrittenEvent` are raised on the game's main thread in the client world's next Pre; events of a client world that has ended are dropped. A declaration rebuilt for another world needs a game restart. New template `kiln-client-program`, analyzer rule KILN109, lint and SDK checks for `"world"` (`world.programs.client`).
- EMF mods: `register_program`, `register_program_def` and `on_event` with `EMF_WORLD_CLIENT` now run in the client world, hosted or joined; a dedicated server refuses them as before.
- **A native can read and write other entities.** Inside a same-step native, `NativeContext.TryRead<T>` and `TryWrite<T>` reach the components that the game's Impact program itself declares, on any entity (the caster's target, for example), in the same step; a type the program does not declare answers false and touches nothing. A write raises `ComponentWrittenEvent` with `Writer = "<modid>/native:<name>"`, and writing an attribute type runs the game's attribute formulas. `NativeContext.Post` defers work to the tick thread. Kiln checks its view of the program against the running game at the first native call of each world and keeps the feature off when it does not match, and it is on only while the game runs that program serially on the world's thread, as the shipped game does (`abilities.natives.ecs`, server only). A write that faults is not rolled back, and the write-event queue is bounded.
- **A block effect can run your native first.** `EffectBlock.Run` (JSON `"run"`) names an `[ImpactNative]` method (`Natives.<Name>`, or a native from a mod's `impact/natives.json`); the effect's program calls it first, in the same step, with its parameters bound by name (`self`, `target`, `attacker`, `caster`, `position`, `attackMod`, `damage`), so a weapon's or a perk's hit can change its own `attackMod` before the damage is dealt. `kiln-manage lint` reports a parameter that binds to nothing as KL340. Server only; `attackMod` or `damage` needs damage in the effect (or an `Optional` parameter).
- **Sample and unit tests for natives.** `mods/samples/FrostMark` is a sword whose hit effect runs an `[ImpactNative]` that makes hits on an enemy below a quarter of its health 1.5 times as hard, with an attachment that counts the Fireball explosion's `applyDamage` calls (`/frostmark`). Kiln.TestKit's `kiln.ImpactNatives` runs your `[ImpactNative]` methods, `RegisterSync` natives and attachments offline: the test declares the game programs it attaches to (`AddProgram`) and makes each call itself (`Call`); programs, attributes and their formulas stay offline.
- `abilities.natives.sync` and `abilities.natives.attach` are decided before your mod's `OnLoad`, so `if (Capabilities.Is("abilities.natives.attach")) Abilities.Natives.Attach(...)` works there; an attachment made then is `Pending` until the world's programs are in.
- Native mods: `kiln_world.h` and `kiln_abilities.h` no longer both define `KilnProgramInfo`: the structs are `KilnWorldProgramInfo` and `KilnImpactProgramInfo`, and the old name stays as an alias in whichever header you include first, so a plugin can include both.
- **`[ImpactNative]`: a C# method becomes an Impact native.** Put `[ImpactNative]` on a static method with typed parameters and the build generates its registration as a same-step native, its typed `impact/natives.json` entry and a `Natives.<Name>` reference for your programs; a shape it cannot make is a build error (KILN170 to KILN174). See [impact.md](../modding/impact.md).
- **Same-step natives and attachments while a mod unloads.** A mod's natives and attachments take no new call once the mod unloads or reloads or the world stops, and its `OnUnload` waits for a call that is still inside: the host keeps the mod, says in `kiln.log` what it waits for, and unloads it in the first step after the call has left (a reload's new load waits with it; at shutdown the host waits 5 s and then skips that mod's `OnUnload` rather than run it under the call). Mods without same-step natives or attachments unload as before. (Kiln's own services close their admission in a new internal step before `OnUnload`; it is not mod API.) A handler still inside after a second is named in `kiln.log` with its native and its mod: a handler must not block. `Abilities.Natives.StateOf` (Waiting, Live, Refused, Dead) and `NativeAttachment.State` (Pending, Active, Off, Gone) say where a native or an attachment stands, and `Abilities.Status` counts attachments by state. An attachment to a program that is registered later turns on when that program goes in. A native accepted before a world exists that the world then has no room for posts `NativeRegistrationRefusedEvent`.
- **Equipment sets.** `Items.CaptureSet` reads a player's 20 equipment slots, `Items.PlanSet` says what applying a set would do without doing it, and `Items.EquipSet` applies it in one transaction: every slot changes or none does (the one exception is `InvariantFailure`: the game left the inventory neither as asked nor as before, or faulted inside the transaction; the reason then says the inventory may be in an unknown state, and sets and single equips switch off until the server, or the hosting player's game, restarts), with one `PlayerEquippingEvent` (a `SetEquipmentChange`) deciding the whole set, `EquipmentSetChangedEvent` / `EquipmentSetFaultedEvent`, and a result that says exactly what changed (`items.equip_sets`, server side). Sets live for the current world session only; the hotbar and the main hand are not touched. On this game build a set that gives more than one already-filled slot a different item is refused before anything changes (`UnsupportedSwaps`): split it into two sets. Backpack changes in a set are refused for now.
- **Buff clones: room for 4,096 per process, all mods together** (1,024 before). `Content.Buffs.GetBudget()` says how much is left. `Content.Buffs.Define(clone, new DefinitionRegistrationOptions(...))` answers Registered, AcceptedNextStart or Refused with a code and a reason instead of throwing, and `GetRegistration(id)` reads the answer later; a definition accepted for the next start is stored under `kiln/data/gamedata/pending/<mod>/` and replayed at the next start, once that mod is loaded again: while the mod is switched off or removed its stored definition stays where it is and nothing registers (`kiln.log` names it once). The store holds at most 4,096 definitions of at most 64 KiB each; Kiln writes it with a flush before the rename, and refuses a link placed at the store's folders or files (the path above `kiln/data` is yours and may contain links). Define many buffs in a data pack or before the world loads, so they are published together (one table for the batch; a buff defined from code while a world runs still gets a table of its own). New refusals with a reason: buff id 0, a game buff's id, another clone's id, room full. If the larger room cannot be reserved next to the game's data, it stays 1,024 and `kiln.log` says so (`gamedata.expanded_buff_room`).
- **VFX resources: a budget you can read, and a definition with an answer** (game clients). `Vfx.ResourceBudget` says how many VFX resources the game holds, how many the game and Kiln's mods use and how many are left (473 for all mods together on this game build), read from the game's own table once a client world runs. `Blocks.Define(name, VfxBlock, options)` answers registered, accepted for the next start, or refused with a code and a reason, and `Blocks.GetVfxRegistration(id)` reads the answer later (`vfx.budget`, `blocks.vfx_registration`). The game's limit itself is unchanged in this release.
- **The NPC roster holds 128** (the game's 35 included, so 93 for all mods together; 64 before). The game keeps unlock states in one 64-bit value; past 64 entries Kiln keeps a second unlock page beside each world's NPC registry (`npcs.expanded_roster`), installed only when a mod's roster needs it. A roster this game cannot hold (129 or more, or 65 or more where the page cannot be installed) stops the start before any world loads, the same way with or without boot mods: `kiln/state/roster-refused.json`, an error line naming the mods, kiln.boot's stop (`boot.json` `boot.stop`, `progress.json` `failed`), on a game client a message box that closes after 60 seconds, then exit code 0x4B02 (status 2 under Wine). It is a start-time act: once a world has run in the process nothing is stopped. Run Kiln as one matched bundle: an older kiln.knowledge cannot be made to stop. No save is opened without the mods' NPCs and knowledge. `kiln.knowledge.npc` answers no unlock state (0xff) for any entry of a roster longer than this side's maximum and names it in `status.reason`; a damaged collection (more than 4,096 entries) is named too, and a roster snapshot after a step whose registry could not be read answers NotReady. A mod's NPCs are ordered by key name, not by file order. New on `NativeQuests`: `GetServerRosterWorld`, `GetClientRosterWorld`, `GetUnlock`, `GetClientUnlock`, `GetRosterBudget` and `RosterUnlockChangedEvent` read unlock states from per-world snapshots on any thread, with a token that ends with its world (`npcs.client_roster_read`).
- **World programs: Kiln and all mods together may register 64** (32 before), and one `kiln.programs.json` may declare 32 (8 before). The last 8 of the 64 are kept for Kiln's own services and loaders. `World.GetProgramBudget()` reads what is left of Kiln's slots and of the world's own table of 896; `kiln.log` names who holds each slot.
- **The capacity types of 0.2.0-dev.28 are no longer experimental:** `NoWarn KILNX028` is not needed any more.
- Native mods: `kiln.hooks` gains `mid2_checked`, `validate_typed`, `sig_status`, `typed_install_ready` and `detour_typed_checked` (the table is 296 bytes; `KILN_HOOKS_ERR_UNCHECKED` when a thread could not be checked and nothing was written). `kiln.abilities` gains `native_register_sync`, `native_counters`, `native_attach`, `native_detach`, `native_declare_typed`, `native_state`, `native_attach_state`, `native_ecs_read` and `native_ecs_write` (312 bytes). `kiln.world` gains six foreign-view members for services that read other entities from inside a program (`foreign_layout`, `foreign_slot`, `foreign_check`, `foreign_read`, `foreign_write`, `foreign_attr_changed`; the table is 496 bytes). kiln-set accepts any `kiln.hooks` table that has the members it calls.

## Fixed

- **Launcher: a selection made right after switching profiles was lost.** The launcher shows the new profile at once and finishes the switch a moment later; that later step cleared whatever you had selected in the new profile in between, and the "Selected mods" bar vanished under your click. The selection now clears once, when the profile changes.
- **EML mods that bring their own DLL and need ShroudForge to load it** (Quiver & Spellbook) now run whole when your profile has no ShroudForge mod: Kiln starts ShroudForge for them by itself. Before, only the mod's data was applied, its extra slots never appeared, and the mod's own page warns that the game drops what is in those slots at the next save in that state. Where ShroudForge cannot run (its part of Kiln is not installed, or you switched it off), the mod is skipped entirely with the reason, never half. After updating, start once and check that the mod's slots are there before you save.
- **ShroudForge mods that spawn things into the world** (SpiderHook's grapple, for one) did nothing under Kiln: Kiln changed the start of five of the game's building functions for every player, and ShroudForge reads one of them to find the game's spawn code. Kiln now leaves those functions alone unless one of your Kiln mods uses the gameplay service (build events, protection zones). With such a mod in your profile, the ShroudForge that Kiln ships now finds that code anyway: its search reads through a function another module has detoured, and only through one that still belongs to the game's own image ([frostdev-ops/shroudforge#1](https://github.com/frostdev-ops/shroudforge/pull/1) by AlexK-Notable, with a follow-up of ours; Kiln's ShroudForge is now built from that merge). Seen on a lab server only (with a mod that uses building the hooks go in before the world starts; with none the five functions are untouched); SpiderHook itself has not been run, and the new search has run in ShroudForge's own tests only, not in a game or on a server with a spawning mod.
- **A visual effect or material a mod defines for the next start is saved whole or not at all:** a crash during the save no longer leaves a broken file behind.
- **EMF mod windows grow with what is in them.** A window of an EMF mod (the Beastmaster stable, for one) kept the height it had when it opened, so a list that filled in afterwards needed a manual resize or scrolling. It now follows its content, up to 85 % of the screen height, and scrolls past that, as under EMF's own loader. Not looked at in a game yet.
- **Frame generation mods (NVIDIA Streamline) no longer crash the game at start.** Kiln's overlay and Streamline wrap the same graphics calls. When Streamline is installed, Kiln now leaves only the overlay's drawing off: your mods' key bindings, the entries mods add to the game's menus and mod loading at the menu keep working; mod windows, on-screen drawing and screen effects are off, and the Mods entry says why. `KILN_UI_OVERLAY=1` tries the drawing anyway, `KILN_UI_OVERLAY=0` switches it off yourself. Not yet tried on a PC with such a mod.
- **If the game closes while Kiln's overlay is starting, the next start leaves the overlay's drawing off** and says why in `kiln.log`, instead of crashing the same way again; after a start that ran a minute, the one after tries the overlay again.
- **Linux (Proton), with Ultimate ASI Loader chained:** the launcher's Steam launch option now names `xinput9_1_0` as well (`WINEDLLOVERRIDES="dinput8,xinput9_1_0=n,b" %command%`), and it tells you when only that part is missing. Before, it showed "Already set" while Valve's Proton loaded its own `xinput9_1_0` and the loader's `.asi` plugins never started.
- **EML mods: a failed start says why.** When Kiln's EML loader could not prepare the game's data, every EML mod showed only "the EML run failed (Failed to create AppState)". The log and each mod's status now name the step and the cause (for example a backup of the game's data that no longer matches what Kiln recorded, with what to do: verify the game files in Steam, then start through Kiln again).
- **A boot mod's own icons show from the first start.** An item or a skill-tree talent that a boot mod makes with an icon of its own showed the icon of the game item or skill node it was made from.
- **Shroudtopia mods that are only a DLL** are now switched on. Such a mod stayed off for good although your profile had it on, because nothing ever wrote its entry in Shroudtopia's settings; Kiln now writes it at the mod's first start. A mod you switched off there yourself stays off, and Kiln's in-game list says where an off Shroudtopia mod is switched off.
- **A Shroudtopia mod that is switched on but never reports itself active** showed as "inactive", and `kiln.log` got an `Activating:` line twice a second. Kiln calls such a mod's `Activate` on every update, as Shroudtopia's own loader does; it now says so once, and the in-game list shows the mod as "activating" with the reason (the mod may not support this game version) instead of sending you to a setting that is already on.
- **Auto Loot Plus next to Ultimate ASI Loader:** Kiln now loads Ultimate ASI Loader after Kiln and keeps Auto Loot Plus first, whatever their "Load after Kiln and ShroudForge" switches say, so Auto Loot Plus can hook the game first and its F8 menu comes up. The profile page shows both switches held by Kiln's rule and says why. Kiln recognises Auto Loot Plus by the folder its package brings (`mods/auto-loot-plus`): if you imported only its DLL, or renamed it, set Ultimate ASI Loader to load late yourself. (Its looting needs an Auto Loot Plus build made for the current game version; that part is the mod's.)
- **Windows, with ShroudForge mods in the profile:** EML mods that come with their own DLL (Auto Loot Plus, Endless Chests) now switch on. Kiln placed them in the game's mods folder but never turned on ShroudForge's switch for them, because ShroudForge writes that folder as `\\?\C:\...` and Kiln compared the two spellings letter by letter. If you made an `extended.mod.json` by hand as a workaround, leave it: Kiln takes it as its own switch.
- The launcher no longer says "Kiln has said nothing for ... s" for a whole session while you play. A start whose main menu Kiln did not see now ends at your first world, and kiln.log names what did not come.
- With more than one chained `dinput8.dll` mod (Spawn the World and Auto Loot Plus, for example), Kiln's in-game mod list no longer shows a "Message From Dear ImGui" popup under them, and each one can be picked on its own. Kiln also turns that developer popup off for every window it draws, mod windows included.
- On Windows, Kiln's in-game Mods page treats ShroudForge's mods folder as the same folder however ShroudForge spells it (`\\?\C:\...`): an EML mod Kiln placed there shows ShroudForge's switch correctly and is no longer called a mod you put there yourself.
- A mod's settings page in Kiln's menu says when its settings file could not be saved (a read-only folder, a full disk), also when the mod saved it itself, until a later save works.
- The proxy's log (`kiln\logs\proxy.log`) now names a line of `dinput8-chain.ini` that was skipped because it does not name a `.dll` (a mistyped file name, an `.asi`). Before, such a line was skipped without a word.
- A boot mod's resource patches can no longer be lost without notice: if the game's resource service was already up before the boot generation was ready, the mod is refused (left out, or the start stops for a `"required"` mod) and kiln.log says why, instead of the mod loading while the game keeps its own values.
- A `"boot": "required"` mod with a broken VFX or material file now stops the start in a player's game, as it promises, instead of loading without that file. (Its valid files work as before.)
- Hosting one world after another: a brand-new world's kept terrain chunks (written before its first save) no longer land in the record of the world you had open before.

## Known limits

- **The 128-entry roster is verified on dedicated servers only.** In a game client, a hosted world included, a missing second page is not computed again, so its locked NPCs from index 64 up are kept until the game's next evaluation. A world saved while a page is missing keeps such a locked NPC, and the first cleanup after a page exists again removes it; pages are not saved, and nothing unlocked is ever removed by being kept.
- **Back from a test build to 0.2.0-dev.28:** dev.28 does not know test builds, so after a switch back to it the game keeps the test build's Kiln until you install Kiln again on the launcher's Runtime page. From 0.2.0-dev.29 on, Play does that by itself.
- **A roster past 64 NPCs and an older Kiln:** a world whose mods add more than 29 roster NPCs, opened with a Kiln before 0.2.0-dev.29 (which refuses that roster), loses those mods' NPC and quest progress when it is saved. Update Kiln on the server and in every player's game before such a mod is added.
- Kept earlier versions: a roll back's settings wait when the game folder has moved since they were kept (the launcher says so); a 0.2.0-dev.28 launcher shows a kept version as one more version and its Clean up may remove it.
- **Values and slots in the game UI** (`ui.values.*`, `ui.slots.inspect`) exist only on a game client, never on a dedicated server; hooks install on first use by a mod, and after a game update these rows stay off until Kiln is updated for that client build.
- **Receiving replication** (`repl.client`) is still unavailable: there is no receive implementation in this build; opening its gate changed no feature behavior, and `11-repl.receive-watch` has no implemented guided check yet.
- **Transform scale accepts any finite positive size on any entity with a writable transform**, including players, occupied mounts and physics bodies; no safe range or entity-family restriction is enforced, and extreme sizes can break downstream calculations. Collision, interaction and attachments keep their sizes.
- **A kept scale is reapplied by template and position.** Kiln replays it only when exactly one candidate is there and drops the record of an entity that was destroyed or replaced, but the identity is positional, not proof: a single other entity of the same template at that place can still get the scale. Removing a mod in a running world does not restore its live scales; the tested chest reloaded at its original size without replay, but other entity families have not been established.
- **Moving a world to another PC without `kiln/data`:** the world save alone does not carry the overlay ledger and witness, so Kiln reads the cells first. Where a quarter or more still match, nothing is written and the overlay waits for adoption; an overlay of which a player removed more than three quarters is written again, including ground the player dug away.
- **Terrain overlays share one work budget per host** (4,096 written and 32,768 read cells, 2 ms a step, for all mods together), so several mods slow each other down rather than the tick; host frame time has not been measured with players.
- **Boot mods next to other loaders' mods on a game client** were confirmed in one hosted game; the guided check of both loader orders (`08-loader-order`) has not been played yet.

- **Required boot VFX:** read or cook failures can stop startup, but the capability row does not prove successful initialization, and a late shader-binding mismatch can remove effects after commit without reporting a required-content activation failure.
