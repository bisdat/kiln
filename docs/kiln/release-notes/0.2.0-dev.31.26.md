# Kiln 0.2.0-dev.31.26

Greeneye Loader mods such as Hollow Halls Progression now read the same game code they found, also where Kiln or
another mod has hooked the game. When a Greeneye mod still does not start, kiln.log says what it asked for.

## Players and server admins

- **Hollow Halls Progression should start again next to Kiln's newer hooks.** On 0.2.0-dev.31.24 it stopped at the
  start with "unsupported game signatures; no map menu", and the launcher listed it as "did not start". The same mod
  had started on the same game build under Kiln 0.2.0-dev.29.19. Since then Kiln's own features hook more places in
  the game, and that start also had a ShroudForge mod (fcu-render-observer) hooking ten more. Kiln's Greeneye host still
  found the game code the mod asked for, but when the mod then read bytes inside that code, it got those hooks' jumps
  instead of the game's own bytes. Now it gets the game's own bytes, the same ones it found. This is the most likely
  cause, but nobody has run the mod with this version yet.
- **When a Greeneye mod does not start, kiln.log says more.** Just before its "did not start" line there is now a line
  with how many game signatures the mod asked for, which ones were not found, which of its reads came from under
  another mod's hook, and where Kiln read the game's code. If every signature was found and the mod stopped by itself,
  the line says it declined for a reason of its own; the mod's own lines above it say which. If a Greeneye mod still
  does not start for you, send a support report (Logs > Save report).
- **Thanks** to Dark-Thoughts for the report and the support report zip (kiln#157).

## Modders

- No mod API change: mod API 0.2.26, as in 0.2.0-dev.31.25, and no signature or enum change. The MDK packs are
  0.2.0-dev.31.26.
- **GreeneyeHost `read` returns the code `find` matches** (`native/plugins/greeneye/src/find_code.h`). `find` matches
  the exe file's relocated `.text`, so another module's hook cannot hide a signature. `read` returned the live bytes
  with only Greeneye's own hooks laid back, as Greeneye Loader does, so a mod that found a pattern and read an operand
  inside the match (a call's target, a global's displacement, a struct offset) got the bytes of a Kiln detour, a hosted
  ShroudForge hook or another loader's jump there. Now `read` returns the exe file's bytes under every recognised hook
  form: a jump to outside the image with the nops behind it, or a call sent outside the image, also one written after
  the first `find`. A byte another mod changed in place is still the live one, as in `find`. A place with too many
  in-place changes to sort (more than 1% of the read and the 4 KiB on each side of it), and every read while `find`'s
  code is the live snapshot, return the live bytes as before. A jump or call to outside the image that a mod wrote
  itself, not through `hook` or `redirectCall`, also reads as the file's bytes: read the memory directly for live bytes.
  The lab probe's `lab_read` check expects the file's first byte now. See docs/kiln/engines/greeneye.md, "Why `read`
  differs from Greeneye Loader's".
- **`find` without the plugin's own exe read.** When kiln-greeneye cannot open, map or match the exe file, it reads the
  same code through kiln.hooks `read_original` (Kiln's verified view, the code sigdb scans), 64 KiB at a time, and keeps
  the live code's in-place changes as before. Only without both does it fall back to the live snapshot and the lookup
  behind hook jumps.
- **kiln.log for a mod that does not start.** `[greeneye] <name>: while starting it asked find for N signatures in the
  game's code (<source>); not found: K ("<pattern>", ...); M reads returned the game's own bytes under another module's
  hook (rva 0x..., ...)`, before the mod's outcome. Up to four patterns (cut at 72 characters) and four places are
  named. `<source>` is `exe file`, `exe file (Kiln's view; the plugin's own read: <why>)` or `live: <why>`; a mod that
  asked `find` for nothing gets "asked find for no signatures" instead. "; so it declined for a reason of its own"
  ends the line only when every signature was found and `GreeneyeModStart` itself returned false; a mod that crashed,
  had a hook refused or failed later gets no such ending (its outcome says why), and no line when it asked nothing. A
  mod that starts gets the reads part only, and only when it has such reads. Quick Deposit's startup line uses the same
  `code=` words.
- `kiln::pe::other_differences` (`native/core/src/pe_text.h`) takes an optional code section span, so a redirected call
  is still a hook when only a window of the code is compared and its original callee lies outside that window. Without
  the span it behaves as before; sigdb and Shroudtopia's original-code paths are unchanged.

## Not yet seen in a real game

- Not tried with Hollow Halls Progression in a game: its DLL is not in Kiln's tests, and neither are those of the other
  Greeneye mods Kiln lists as supported (The Worst Map Mod, Find, Quick Deposit, Town Portals, Embervale Teleport),
  so none of them has run against the new `read`. From the reports: the same DLL (sha256 0e08ac7e...) started on the
  same exe (client 26430625) under 0.2.0-dev.29.19 on Windows, hosted ShroudForge's two main menu call relays included
  (a player's report of 20 Nov 2026). The 31.24 start's `hooks.json` lists 40 hooked places that one's does not: 30 of
  Kiln's newer detours and fcu-render-observer's 10. Over a copy of client 26430625 with the player's 135 hooked places
  rebuilt, `find` saw no byte different from the exe file, and reads of the 74 patterns over those places that are
  unique in the file gave the hooks' bytes before this change and the game's own bytes after it. Which read the mod
  makes is not known. If it still does not start, the new kiln.log line names the signature or the read.
- The fallback to Kiln's view of the exe has not run in a game: every report that shows the source (Quick Deposit's
  `code=exe file`) had the plugin's own read.
