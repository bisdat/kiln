# Kiln 0.2.0-dev.31.next: stale game data

## Players

- **Kiln no longer keeps an uninstalled mod's changes in your game data.** Kiln, and the ShroudForge that comes with it, start every mod pass from a clean copy of the game's data files. That copy could be taken from game files that another mod loader had already changed. It then kept that mod's changes long after the mod was removed. For one player, Auto Loot Plus's auto-smash stayed for weeks: props broke on their own within 15 m, through walls, with Kiln Auto Loot switched off. Kiln now checks the clean copy against Steam's own list of the game's files before every pass. A copy that doesn't match is set aside (never deleted) and taken again from your game files when those are Steam's. When they aren't either, Kiln changes nothing, and the launcher and kiln.log say: "Your game files still contain changes from a mod that isn't installed. Verify the game files in Steam (Properties > Installed Files > Verify integrity), then start again." Until you do, ShroudForge's mods don't load. Thanks HadToRegister for weeks of reports, and for the Steam file check that found it.

## Modders

- No API change. The working baseline record (`enshrouded.kfc.baseline.json`) now keeps each backup's SHA-1. ShroudForge's prepared record moves to scheme `kiln-sf-prepared 3`, so the first start after this update runs its pass once. kiln-eml accepts scheme 3 as hosted ShroudForge output. Without a Steam manifest (a SteamCMD server, a game folder outside a Steam library), a clean copy is refused only when it holds a known mod's program (for now, Auto Loot Plus's auto-smash program and aura).

## Not yet seen in a real game

- The refusal and the retake on a player's real game folder (Windows, Linux/Proton, Steam Deck), and the first start's one extra read of the clean copy (about 225 MB) after updating.
