# Kiln 0.2.0-dev.31.29

Windows 11 players with a mod that has its own models, materials or textures (Flamebound Ledger, for one) could crash in
the main menu, a few seconds after it appeared. This release fixes it. Windows 10, Linux and Steam Deck players were not
affected.

## Players and server admins

- **No more main-menu crash on Windows 11 with content mods.** On Windows 11, with a mod that brings its own models,
  materials or textures, the game could stop in the main menu, and the game's own log (`enshrouded.log` in the game
  folder) ended with "error loading streamed texture mip tail: eof reached". On Windows 11 the game reads its files
  through a newer Windows reader, the I/O ring (IoRing). Kiln hands the game a mod's own content only through the
  game's standard reader, so on the I/O ring the game read an empty file instead. Kiln 0.2.0-dev.31.29 has the game use
  its standard reader, the one it uses on Windows 10.
- **On an older Kiln:** add `--disable-ioring` to Enshrouded's launch options in Steam (right-click Enshrouded >
  Properties > General > Launch Options). It makes the game use its standard reader too. After updating to
  0.2.0-dev.31.29 you can remove it again; it does no harm if it stays.
- **The trade-off.** While Kiln runs with its hooks on (every start except safe idle), the game uses its standard reader
  on Windows 11 too, with or without a mod that has its own content: a mod can add content at any point in a session,
  and the reader is chosen once, at the game's start. It is the reader every Windows 10 player has; loading may be a
  little slower than with the I/O ring on some PCs. A start without Kiln, or with Kiln in safe idle, keeps the I/O
  ring. A dedicated server with Kiln on Windows makes the same choice.
- **Support reports spot this crash.** A support report from a Kiln that hit it (0.2.0-dev.31.28 or older) now says
  so, names the mods whose content Kiln served, and names the `--disable-ioring` launch option. To check, the report
  reads the game's own log for those few lines only; nothing of that log goes into the report.
- **Kiln's overlay after this crash.** The crash came seconds after Kiln's overlay drew its first frame, so Kiln's crash
  guard took it for an overlay problem and keeps the overlay's drawing off for the next start; the start after that
  tries it again. If kiln.log says it failed twice at this stage, delete `kiln/state/overlay-start.guard` in the game
  folder to let it try again. Key bindings and the Mods menu work either way.
- **Thanks** to Rebur for the report and the crash files (KR-KZRX) that pinned it down.

## Modders

- No mod API change: mod API 0.2.26, as in 0.2.0-dev.31.28, and no signature or enum change. The MDK packs are
  0.2.0-dev.31.29. Nothing to change in a mod: the blobs Kiln serves (cooked models, materials, textures, VFX, and
  blobs added or overridden through kiln.assets) are served as before.
- **The cause.** The game's async IO (GameFramework "AsyncIo") takes the Windows 11 I/O ring when `kernelbase.dll` has
  it: it loads kernelbase and asks `GetProcAddress`, through the exe's own KERNEL32 import, for
  QueryIoRingCapabilities, CreateIoRing, IsIoRingOpSupported, GetIoRingInfo, SubmitIoRing, CloseIoRing,
  PopIoRingCompletion, SetIoRingCompletionEvent, BuildIoRingReadFile, BuildIoRingRegisterFileHandles and
  BuildIoRingRegisterBuffers, then reads every container through the ring ("Using IoRing for async io..." in
  enshrouded.log). Kiln answers its own container (the empty `kiln/data/assets/kiln-content.dat`, where the merged
  content map points mod blobs and overridden game blobs) only at the game's ReadFile and CreateIoCompletionPort
  imports. On the ring the game read the empty file itself: "PopIoRingCompletion returned with error ...
  result-code:0x80070026" (end of file), and the first material texture whose mip tail failed hit the game's deliberate
  fatal (client 26430625, exe+0xb90a5).
- **The fix.** While Kiln's content path is on (its KfcContentMap and AsyncIoCreate hooks are in), kiln.assets also
  patches the exe's `GetProcAddress` import slot: a name with "IoRing" in it is not found (ERROR_PROC_NOT_FOUND), and
  every other name and every ordinal reaches the import as before (a tail jump, so the caller is still the game). The
  game then logs "[os] Could not find IORing Api function 'QueryIoRingCapabilities' - IORing not available" and makes
  its ReadFile and completion port queue, the path Windows 10 and Proton take, which Kiln answers. Only the exe's own
  import changes: other modules (ReShade, Streamline, overlays, ShroudForge's own libraries) resolve the I/O ring as
  before. The slot is patched during Kiln's boot, at the game's entry point, before any game code runs; the game's
  AsyncIo init comes later (in KR-KZRX: kiln.assets hooked at 14:30:15 UTC, the game's log began at 14:30:31 and chose
  the ring 3.9 s after that). The dedicated server resolves the ring the same way (server 26430253) and gets the same
  gate. A start whose content path is off (a refused hook) keeps the game's I/O ring.
- **kiln.log.** At start: "assets: content reader hooked; the game's async IO is kept off the Windows 11 I/O ring ...".
  Once, when the game asks: "assets: the game asked for the I/O ring API (QueryIoRingCapabilities): not found ...". Then
  "Kiln's container joined the IO completion port", as on Windows 10 and Proton. "Kiln's container did not join the
  async IO queue's completion port: the game reads it another way ..." is a warning that the game still reads the
  container some other way; `--disable-ioring` is the workaround then. If the exe's GetProcAddress import slot is not
  found, kiln.log says so at start.
- **Support report finding `ioring-kiln-content`** (a problem): the game's `enshrouded.log` (its last 4 MiB, read for
  these lines only and never zipped) shows the I/O ring and has the mip-tail fatal or the ring's end of file, and
  kiln.log's last boot served content blobs ("content map rebuilt: ... + N Kiln entries", N > 0). Windows 10, Proton and
  a start off the ring are never this finding (review-3129), and neither is a vanilla mip-tail failure on a Kiln that
  served no blob. docs/kiln/launcher/support-report.md has the full rule.
- Tests: the assets host suite compiles the production `hk_GetProcAddress` over a fake import (every I/O ring name
  refused and said once in kiln.log; other names, null and ordinals reach the import) and checks that the slot is
  patched only after the content hooks (`run.sh`, 399 checks); kiln-manage's report tests cover KR-KZRX's own lines, the
  ring's end of file alone, Windows 10 and Proton logs, a boot with no Kiln blob, an older boot and a drop-in mod.

## Not yet seen in a real game

- Nobody has started Windows 11 with this build yet. The fix rests on Rebur's crash files, static analysis of client
  26430625 and server 26430253, and host tests. With it, the game's log should say "IORing not available" and kiln.log
  "joined the IO completion port".
- Loading times on Windows 11 with the standard reader against the I/O ring were not measured.
