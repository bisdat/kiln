# Kiln 0.2.0-dev.31.next: ShroudForge world edits in a joined game (draft lines for the bundle)

## Players and server admins

- **A ShroudForge mod that changes blocks now tells you why it does nothing in a game you joined.** Only the server, or the player hosting, can change the world's blocks, in ShroudForge as with Kiln, so a mod such as Altar Cleanup has to run there. In a game you joined, it waited and gave up with nothing on screen, and kiln.log had only ShroudForge's own "original registered voxel grid contract is unavailable" or "voxel write was rejected before changing the world". Now Kiln shows one message over the game, "A ShroudForge mod tried to change blocks, but in a joined game only the server or host can. Run that mod there.", once per joined game however often the mod tries again. kiln.log gets one line that says the same and names the mod when its own log line shows which one. Thanks to netjunk for the report from a client joined to a dedicated server.
- In the same report, Altar Cleanup ran in netjunk's own hosted world: its "waiting: voxel grid: voxel-grid-pending" lines last for a moment while the world loads, then it scans, cleans up and undoes as it should. That is not a fault.

## Modders

- In a joined game, ShroudForge's answers stay as ShroudForge has them: `runtime.world.voxel.get_grid_spec` answers `nil, "original registered voxel grid contract is unavailable"` (it never becomes ready there), and `runtime.world.voxel.write` is unavailable and answers `false, "voxel write was rejected before changing the world"` (outcome 1). Kiln adds only its kiln.log line and the toast. In `kiln/state/shroudforge.json`, `joinedWorldEdit` is `{session, mod, at}` for the last joined session it happened in (`mod` is `""` when no mod's line named it).
- The kiln.log reason of Kiln's voxel writer in a joined game is now "this game joined a server, and only the server or the player hosting can change the world's blocks; a ShroudForge mod that changes blocks has to run there (ShroudForge works the same way)"; with no world at all (the main menu) it is "no world runs in this game as its host yet".
- **World edits in multiplayer** ([shroudforge.md](../shroudforge.md#world-edits-in-multiplayer)): ShroudForge's own pattern, the same mod on both sides: the joined game sends with `runtime.network.send_mod` to `status().session_host_steam_id` (or `remote_dedicated_server_steam_id`), the server reads `receive_mod`, checks `runtime.network.player_permissions(peer_steam_id)` (`CanEditWorld`, ...) and writes.
- Under Kiln, ShroudForge's network transport is ShroudForge's own on both sides. On a Kiln dedicated server (a Linux lab server, Kiln 0.2.0-dev.31.19, with the probe below) ShroudForge's network service comes up with role `server` within about 4 s ("Network service is ready. Automatic Steam session acceptance and authenticated-peer health probes are active"), `status()` reports `available`, `service_ready` and the server's own Steam ID, and `send_mod`, `receive_mod`, `connected_peers` and `player_permissions` all answer (an unknown peer: "this player is not in this game or has not logged in yet"). In netjunk's game client joined to a dedicated server (31.19) it came up with role `client` too. A message from a joined game to a Kiln dedicated server has not been seen yet (it needs a real game client). For that check, Kiln's repository has `mods/tests/sf-net-probe` (`kiln-sf-net-probe`): install it on both, join, and read the `net-probe:` lines in both kiln.logs.
- Kiln mode (Kiln's interpreter for ShroudForge mods) has no voxel write yet, hosted or joined; in a joined game its `get_grid_spec` gives ShroudForge's same answer, without the message.
- No mod API change.

## Not yet seen in a real game

- The toast and the kiln.log line in a game client joined to a server (host tests and a Wine test of the writer only).
- `runtime.network.send_mod` from a joined game to a Kiln dedicated server, and the answer back (the probe pair ran against each other in a host test only).
