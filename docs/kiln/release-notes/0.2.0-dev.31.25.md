# Kiln 0.2.0-dev.31.25

Mod cameras can now go anywhere in the world instead of staying within 250 m of your character, and players with an NVIDIA Streamline or OptiScaler frame generation mod can choose to draw Kiln's overlay anyway. The launcher's AppImage shows up once in the app menu under Gear Lever, Install and Repair no longer refuse Ultimate ASI Loader under two names, EML mods wait for a file the game you just quit still holds, and a mod's Settings window opens the settings file the mod reads.

## Players and server admins

- **Mod cameras can now go anywhere.** A mod's camera (a cutscene, a follow view, a riding view) no longer has to stay within 250 m of your character, and Kiln no longer caps how far behind or above its target a follow camera sits. A mod can now show, for example, your whole base from 300 m straight up. Far from your character you see the world as the game has it around you: things the server only sends near your character (creatures, other players, dropped items) can be missing in a view of a place far away.
- **A mod camera keeps going through a hitch.** A cutscene path or a camera shake used to stop when the game's simulation paused for a quarter of a second while the picture kept drawing. It now plays on. A camera that follows something still stops if it loses track of it.
- **Both ends need this version for the bigger numbers.** On a server, a mod's camera request beyond the old limits is refused by a client that still runs an older Kiln; that player keeps the game's own camera.
- **Draw Kiln's overlay anyway, from the launcher.** With an NVIDIA Streamline frame generation mod in the game folder (`sl.interposer.dll` there or in `Streamline/`), Kiln turns its in-game overlay off by itself, because the two together crashed the game at start in 0.2.0-dev.29, and every HUD mod (Grimoire's, for one) went with it. The only way to draw it anyway was the launch option `KILN_UI_OVERLAY=1`, which Steam cannot set on Windows. Now the Play page shows NVIDIA Streamline with a switch under it: **Draw Kiln's overlay anyway (may crash at start with frame generation)**. Settings, Graphics has the same switch, and so does OptiScaler's banner when its own menu or its frame generation keeps Kiln's overlay off. It applies from the next game start; switching it off gives the choice back to Kiln.
  - **By hand, on Windows and Linux:** in the game folder's `kiln/kiln.json`, put `"overlay": "on"` in the `"ui"` section, for example `{ "ui": { "overlay": "on" } }`. Exactly `"on"`: anything else lets Kiln decide. Settings, Advanced, Kiln's file offers auto, off and on under "Kiln's overlay". On Linux, `KILN_UI_OVERLAY=1 %command%` still does the same and wins over the file, and `KILN_UI_OVERLAY=0` still keeps the overlay off whatever the file says.
  - **What it risks.** "on" does exactly what `KILN_UI_OVERLAY=1` does. Kiln still records each start, and `kiln/logs/kiln.log` says when the game closed while the overlay was starting, but while the switch is on Kiln tries the overlay again at every start. **If the game keeps closing at start, switch it off**, in the launcher or by removing the line. Kiln then steps aside by itself again, and its record still counts: after two closes at the same stage it keeps the overlay off until you delete `kiln/state/overlay-start.guard`, switch it on again, or update Kiln.
  - **Only the overlay.** Kiln's frame cap, DLSS settings and upscaler still step aside for Streamline and OptiScaler. The readout is part of the overlay: next to those tools it shows only while the switch is on, and Settings, Graphics now says so instead of "the readout still works". OptiScaler's banner on the Play page says when the overlay is drawn anyway.
  - **The Mods entry names the setting.** With the overlay off for Streamline or OptiScaler, the game menu's Mods entry reads, for example, "Mods: the overlay's drawing is off: NVIDIA Streamline is installed (kiln.json ui.overlay "on" draws it anyway)".
- **Kiln Launcher shows up once in the app menu when Gear Lever installed it.** Gear Lever, AppImageLauncher and appimaged add their own app menu entry for an AppImage. The launcher added one as well, so the menu and Gear Lever's list showed "Kiln Launcher" twice, and removing one in Gear Lever uninstalled the whole app. On Bazzite, Silverblue and Kinoite the two even looked different (`/home/...` and `/var/home/...` are the same folder there). Now, when such a tool has added Kiln, the launcher adds no entry of its own and removes the one it added before. Entries made by Gear Lever or by you are never touched. Nexus Mods "Mod Manager Download" links and `kiln://` links work as before, and Kiln's icon stays. Settings, Appearance, "Kiln Launcher in the app menu" then says "Gear Lever (or another AppImage integrator) already added Kiln to the app menu" instead of offering a second entry; if you switched it off to work around the duplicate, you can leave it off. The .deb, the .rpm, the Steam Deck and an AppImage you run without such a tool work as before.
- **Ultimate ASI Loader under both names no longer stops Install or Repair.** Kiln runs Ultimate ASI Loader as `xinput9_1_0.dll` so that its own loader can be `dinput8.dll`. If Multi DLL Installer or Vortex then wrote Ultimate ASI Loader back as `dinput8.dll`, Install and Repair refused with "can only be chained as xinput9_1_0.dll, and another file has that name". Now Kiln puts its loader in as `dinput8.dll` and moves the second copy of Ultimate ASI Loader to the install's backup in `kiln/backups`; if the two copies are different versions, the newer one is the one that keeps running as `xinput9_1_0.dll`. Your `.asi` plugins load as before, and the launcher's install notes and its log say where the copy went. Any other file named `xinput9_1_0.dll` still stops the install, as before.
- **If the other mod manager deploys it again, Play tells you.** Before, the game started without Kiln and the launcher only said afterwards that Kiln did not load. Now Play stops before the start and says that `dinput8.dll` is Ultimate ASI Loader again and that another mod manager likely put it there: press **Repair** on the Runtime page, and press it again whenever that manager deploys it again. A vanilla start (without Kiln) still works.
- **EML mods no longer all fail because the game was still closing.** On one start, all of sosmic's EML mods failed with `could not copy enshrouded.kfc.bak ... (os error 32)`: another program still had Kiln's backup of the game data open, most likely the game he had just quit, still closing, or an antivirus or backup program. Kiln now waits for such a file and tries again, for about 2.5 seconds, also when it puts the game's own data back over a file the closing game still holds. If the file is still in use after that, the reason in the Kiln menu and in kiln.log is one plain sentence: "another program has enshrouded.kfc.bak open (the game still closing, an antivirus or a backup); try again in a moment". That start runs without the EML mods, as before, and the next start tries again.
- **"Open shroudtopia.json" and "Open extended.mod.json".** In the launcher, Mods, a mod's More menu, Settings: the window has a button that shows the mod's settings file in its folder. For a Shroudtopia mod it is the `shroudtopia.json` of the profile you are looking at, the one Shroudtopia reads; until it exists (Shroudtopia writes it at the first start with that profile, the launcher when you change a setting), a line says so. For a ShroudForge mod it is the copy in the game's mods folder that ShroudForge runs (Kiln's copy, or your own folder of the mod), never the copy in Kiln's Library; while the profile is not the one the game uses there is none, and a line says so.

## Modders

- No mod API change: mod API 0.2.26, as in 0.2.0-dev.31.24, and no signature or enum change. The MDK packs are 0.2.0-dev.31.25.
- **Kiln.Camera keeps only the limits that protect the game.**
  - **No distance from the player.** Path keys and every camera Kiln derives (a profile's output, a shake on top) may be anywhere within the world bound, ±1,000,000 m on each axis, which stays: it keeps every position inside what the engine's 32.32 metres and float maths handle (the map is about 10 km across). Outside it a request is refused `Bounds` before the first frame and ends `SafetyRejected` after it, as before; NaN and infinity, unit rotations and the projection's lens margin are checked as before.
  - **No size caps on profiles and shakes.** `CameraProfile.Distance` is any finite value of 0 m or more (was 0.25 to 200), `OffsetLocal` and `OffsetWorldY` any finite metres (were 100 m and ±100 m). `CameraShake.AmplitudeMetres` and `FrequencyHz` are any finite value of 0 or more (were at most 0.5 m and 0.1 to 30 Hz); the offset is still never longer than the amplitude, and how strong a shake may be is your call.
  - **Lens 1 to 179 degrees** (was 5 to 160), keyed lenses on a path too: the whole degrees inside the 0.01 rad margin from 0 and 180 that the projection takes.
  - **A path, a shake and a lens read no player sample.** Only a follow profile reads a position, its target's, and still ends `SafetyRejected` when that copy is older than 250 ms; it no longer also needs the local player's copy. A path or a shake used to end `SafetyRejected` after 250 ms without a client step; now it plays on, and End's blend out always runs to its end. On a client whose position sampler is off or faulted, `camera.local_pose` and `camera.local_shake` stay on; only `camera.local_profile` goes off.
  - **What a far camera costs.** Kiln moves the picture only. The server keeps streaming around the player's character (its `PlayerFocus`), so a view far from the character can lack what the server sends only near the player. Culling and level of detail follow the drawn camera; Kiln never changes the near and far planes, and fog, sound and the HUD stay the player's. For a place kilometres away, move the player there first. Details: [camera.md](../services/camera.md#a-camera-far-from-the-player).
  - **Older clients.** A client before 0.2.0-dev.31.25 refuses a `Camera.Set` beyond its old limits: `MalformedRemote` for a profile, lens or shake value past the old caps (its wire check), `Bounds` for a path key or derived camera more than 250 m from its player. Nothing changes on that client, and a refused `Update` keeps the lease. `Camera.GetCapabilities` does not tell the versions apart, so a mod that needs the new range should expect those refusals from older clients.
  - **CameraSample's riding view** (`MountFollow.BuildFlyerProfile`) frames any size of mount instead of refusing one taller than 100 m, farther back than 200 m or more than 250 m from the rider. The authoring schema (`schema/camera-override.schema.json`), the XML docs and the agent API index carry the new ranges.
- **kiln.json `ui.overlay` takes `"on"`** next to `"off"` and `"auto"` (`native/services/ui/overlay_setting.h`): `KILN_UI_OVERLAY=1` in the player's file. What wins: `KILN_UI_DISABLE=1`, then `KILN_UI_OVERLAY` set to `0` or `1`, then kiln.json, then Kiln's own decision (the crash guard, Streamline, OptiScaler). The crash guard is the same for both switches: the attempt is recorded before Kiln's first Vulkan hook, a death in it counts at the next start (guarded, then locked at a second one at the same stage), and that start draws again while the switch is on. Players without the switch see no change but the texts below.
  - **`Ui.Status.Error` and the drawing capability rows** for Streamline and OptiScaler now end with "(kiln.json ui.overlay "on" draws it anyway)", as the Mods entry does. A mod that compared the whole text should match its start instead.
  - **Expected with frame generation, not yet seen:** when Streamline's present thread presents through Kiln's hook, draw and pre-overlay callbacks run on that thread, once per frame shown (generated frames too), not once per frame the game renders.
  - **Launcher:** the kiln.json snapshot's `ui.overlay` has the options auto, off and on; `components/OverlayAnyway.tsx` writes `"on"` and removes the key when switched off. kiln-manage's OptiScaler note (`GameStatus.graphicsTools`, the support report) names the switch, and says the overlay is drawn anyway while the game's kiln.json has `"on"` (`game::overlay_anyway`); `kilnOverlay` stays what OptiScaler.ini decides.
- **The launcher under an AppImage integrator** (`launcher/src-tauri/src/desktop.rs`, `Integration::find`). It writes no `kiln-launcher.desktop` and removes its own (the one with `X-Kiln-Desktop-Entry=1`) when `DESKTOPINTEGRATION` is set in its environment (not empty, `0`, `false` or `no`), or when another entry the menu shows (`Type=Application`, not `NoDisplay` or `Hidden`, the first file with its desktop id across `$XDG_DATA_HOME/applications` and each `$XDG_DATA_DIRS/applications`, subfolders included, not under Kiln's own id `kiln-launcher.desktop`) has an `Exec` argument or `TryExec` that is the same file as `$APPIMAGE` once both paths are resolved. `DesktopInfo.integrator` (`app_info`, `app_desktop_set`) holds `DESKTOPINTEGRATION=<value>` or the other entry's file; while it is set, the switch is off and not offered. The icons stay up to date for the NoDisplay nxm and `kiln://` handler entries, which this leaves alone.
- **Ultimate ASI Loader under both names** (`kiln-manage` `install`). When `dinput8.dll` and `xinput9_1_0.dll` (any spelling, plain files) are both Ultimate ASI Loader (its `IsUltimateASILoader` export), Install and Repair are not refused: the newer one by its VS_VERSION_INFO file version runs as `xinput9_1_0.dll` (with the same bytes, the same version or no version, the chained copy stays), the other goes to `kiln/backups/install-*/` and the launcher's second copy, and `..\xinput9_1_0.dll` is added to `chain.ini [chain]` when it is missing. The receipt records the backed-up copy as a `replaced` entry of `dinput8.dll` (`backed-up`, engine `ultimateasiloader`); when the newer copy took the chained name, an earlier install's `chained` entry names the newer bytes. Uninstall gives back the folder Kiln found (or the newer copy as `dinput8.dll`). The install result's `warnings` carry the sentence. A folder, a link or any other file under `xinput9_1_0.dll` is refused as before.
- **Play** (`launch_play`): every mode but `vanilla` is refused (`refused`, `detail.ualOverProxy`) while Kiln's receipt is there and `dinput8.dll` is Ultimate ASI Loader (`install::ual_over_proxy`): those modes need Kiln's proxy (it reads `play-once.ini` and the profile), so the start would not do what was asked. Steam's own Play button is not affected.
- **kiln-eml tries again on a file in use.** The vanilla backup and stage copies, the publication and restore copies, and the renames that set an old backup pair aside are tried again on Windows' sharing violation (os error 32) and lock violation (33). A copy's last step, its temp renamed over the target, is also tried again on access denied (5), but only when the target, opened for deletion with every sharing allowed, answers a sharing or lock violation (another program holds it); a real permission problem (a read-only file, an ACL) fails at once with the system's words. The pauses are 0.1, 0.2, 0.4, 0.8 and 1 s: six tries in about 2.5 s. When the file is still held, the run's `error` and `reason` in `kiln/state/eml.json` are the plain sentence, naming the file, and a kiln.log warning before it gives the paths, the number of tries and the system's own words.
- **`EngineSettings.openFile`** (`engine_settings_get` / `engine_settings_set`; [contracts.md](../launcher/contracts.md)) is the settings file the engine reads, once it exists: Shroudtopia's `<configDir>/shroudtopia/shroudtopia.json` for the profile (the game's copy in Copy mode), and ShroudForge's `extended.mod.json` only in the game's mods folder. It is absent otherwise.

## Not yet seen in a real game

- A camera far from the character: how far the game streams and draws at full detail around a Kiln camera, and what a view of a place kilometres away shows. Host tests and a static read of client 26430625 only. Lenses near 1 or 179 degrees, and shakes above half the frame rate, on screen.
- Kiln's overlay with "on" next to a Streamline frame generation mod: nobody has run it yet. From Streamline's SDK and Kiln's code, where Kiln draws depends on how the mod loads Streamline: on every frame shown (generated ones included) when Streamline stands in for the game's Vulkan loader, on the game's own frames before frame generation when Kiln's hooks end up in front of it (its windows may wobble in the generated frames), and nothing for that session when Streamline presents from a queue Kiln saw it add (kiln.log says "frame generation presents the game's frames from its own queue"). The cause of the 0.2.0-dev.29 crash at start was never confirmed. A tester with an RTX 40 or 50 card and the mod can tell which case it is from kiln.log and the readout's frames a second. The launcher's switch is tested in its preview (mock) mode only.
- Not tried under a real Gear Lever, AppImageLauncher or appimaged install, or on Bazzite: tests with temporary XDG folders cover `DESKTOPINTEGRATION`, a Gear Lever entry reached through a linked `/home`, another AppImage's entry, someone else's file kept, and the Settings line.
- Ultimate ASI Loader under both names has not run with Multi DLL Installer or Vortex in a real game folder: kiln-manage tests over temp game folders cover both copies with the same bytes, two versions both ways, both placed by hand, Repair, a foreign `xinput9_1_0.dll` (still refused), and a re-deploy after Repair (Play refused, then Repair and Play work).
- The wait for a file in use has run against a real file held without sharing on Windows, in host tests, but not in a real start with the game closing or an antivirus holding the backup. The Open buttons are covered by unit and browser tests on the launcher's mock backend; on a real install they use the same command as the launcher's other Open buttons.
