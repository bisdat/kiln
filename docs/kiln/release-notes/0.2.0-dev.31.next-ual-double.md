# Kiln 0.2.0-dev.31.next (ual-double part; work-cm renames and merges this file)

Install and Repair no longer refuse when Ultimate ASI Loader sits in the game folder twice, as `dinput8.dll` and as `xinput9_1_0.dll`.

## Players and server admins

- **Ultimate ASI Loader under both names no longer stops Install or Repair.** Kiln runs Ultimate ASI Loader as `xinput9_1_0.dll` so that its own loader can be `dinput8.dll`. If Multi DLL Installer or Vortex then wrote Ultimate ASI Loader back as `dinput8.dll`, Install and Repair refused with "can only be chained as xinput9_1_0.dll, and another file has that name". Now Kiln puts its loader back as `dinput8.dll` and moves the second copy of Ultimate ASI Loader to the install's backup in `kiln/backups`. Ultimate ASI Loader keeps running as `xinput9_1_0.dll`, and your `.asi` plugins load as before. The launcher's install notes and its log say where the copy went.
- **The newer copy is the one that runs.** If the two copies are different versions, Kiln keeps the newer one as `xinput9_1_0.dll` and moves the other to the backup.
- **If the other mod manager deploys it again, Play tells you.** Before, the game started without Kiln and the launcher only said "Steam did not load it this start". Now Play stops and says that `dinput8.dll` is Ultimate ASI Loader again and that another mod manager likely put it there. Press **Repair** on the Runtime page. To stop it coming back, turn off that manager's `dinput8.dll` deployment (or remove Ultimate ASI Loader from it). Kiln already loads Ultimate ASI Loader for you. A vanilla start (without Kiln) still works.
- **Any other file named `xinput9_1_0.dll` still stops the install,** as before: Kiln never replaces a file it does not recognise. Move it out of the game folder, then install.
- **Thanks to KR-NXM5** for the report.

## Modders

- No mod API change.
- **Installer** (`kiln-manage` `install`): when `dinput8.dll` and `xinput9_1_0.dll` (any spelling) are both Ultimate ASI Loader (its `IsUltimateASILoader` export), the newer one by its VS_VERSION_INFO file version runs as `xinput9_1_0.dll`. With the same bytes, the same version or no version, the chained copy stays. The other copy goes to `kiln/backups/install-*/` (and the launcher's second copy). `..\xinput9_1_0.dll` is added to `chain.ini [chain]` when it is missing. The receipt records the backed-up copy as a `replaced` entry of `dinput8.dll` (`backed-up`, engine `ultimateasiloader`). Uninstall still gives back the folder Kiln found, or the newer Ultimate ASI Loader as `dinput8.dll` when the newer copy replaced an earlier install's chained one. The install result's `warnings` carry the sentence. A folder or a link under that name is refused as before.
- **Play** (`launch_play`): every mode but `vanilla` is refused (`refused`, `detail.ualOverProxy`) while Kiln's receipt is there and `dinput8.dll` is Ultimate ASI Loader (`install::ual_over_proxy`). docs/kiln/engines.md (Installer) and docs/kiln/launcher/contracts.md (Launch) describe both.

## Not yet seen in a real game

- Neither the install nor the Play message has run with Multi DLL Installer or Vortex in a real game folder. Kiln-manage tests cover the player's case over temp game folders: both copies with the same bytes, two different versions both ways, both placed by hand, Repair, a foreign `xinput9_1_0.dll` (still refused), and a re-deploy after Repair (Play refused, then Repair and Play work).
